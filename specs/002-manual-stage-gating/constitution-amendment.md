# Constitution Amendment Proposal 2.0.0

状态：Proposed · 待用户确认 · 不修改现有 constitution 文件

## 变更理由

用户 2026-10-19 明确要求：全自动流程存在问题，改为手动逐阶段；每个环节确认后才执行下一环节。现有 1.0.0 第一章“不恢复手动生成模式，不增加逐阶段确认”与之直接冲突。

## 建议替换条款

### 一、客户目标与自动化边界（替代原文）

客户提交创作要求后，**全站进入手动逐阶段制作**：

- 剧本 → 定妆照 → 镜头 → 成片；
- 上一阶段由用户明确确认后，才允许执行下一阶段的付费生成或合成；
- 打开页面、轮询、刷新、重试不得被当作确认；
- 旧自动执行保留历史/对账兼容，但立即停止自动派发新阶段；
- 已提交上游、轮询或 reconcile 的任务继续核对/结算；未提交 queued 任务取消并释放预占；
- 不退款、不硬杀已付费上游、不重复提交；
- 旧任务结算后，项目进入对应手动阶段，由用户确认后续。

自动模式不再是新项目入口，也不再推进旧项目；`generation_runs`/orchestrator 仅保留历史与对账兼容。

### 二、商业与资金规则保持

价格、积分、预占/结算、退款、分佣、归属、审计规则不变。每个阶段确认只决定**是否派发下一阶段任务**，不改变既有扣费价格和退款规则。

### 三、最小变更

优先复用现有手动接口、jobs、项目状态和审计；不重写交易服务。新增 `workflow_mode`、阶段确认接口或迁移必须说明兼容性。

### 四、隔离验证

测试只使用合成数据、隔离库、模拟上游；不真实付款/退款/生成，不读取生产密钥。

### 五、规范与变更纪律

继续执行 constitution → specify/clarify → plan → tasks/analyze → implement → converge；需求、技术方案、任务分别确认；发现冲突先登记，不直接编码。

### 六、审批与上线

书面规格、技术方案、任务均需用户确认后才实施；部署另行批准。

## 需要用户确认

1. 同意以本修订替代 1.0.0 第一章；
2. 同意全站立即手动、旧执行安全停止与结算；
3. 同意本轮只写规格/方案，不编码。
